 
 Там реально несколько уровней, не путай их между собой:
  
  - Table — логическая сущность (статическая или динамическая таблица в Cypress).
  - Tablet — только для динамических таблиц: шард по диапазону ключей, обслуживается одной tablet node.
  - Store — внутренность таблета: либо dynamic store (свежие данные в памяти ноды), либо chunk store (уже сброшенные на диск чанки).
  - Chunk — физический immutable-блок данных на data nodes (десятки/сотни МБ). На этом уровне живут и статические таблицы тоже.
  - Block — внутренний кусок чанка (обычно ~16 МБ), минимальная единица чтения с диска и кэширования.
  - Chunk slice / data slice — это уже виртуальная штука, не физическая: при планировании чтения или джоба чанк нарезают на подрэнджы по ключу/индексу, чтобы раздать воркерам поровну. На диске никакого «слайса» не существует
   — это просто (chunk_id, lower_limit, upper_limit).

  Грубо: 
  
  **статика — Table → Chunks → Blocks, а при чтении/джобах поверх чанков накидываются slices.** 
  
  **Динамика — Table → Tablets → Stores → (для chunk store) Chunks → Blocks.**


Потому что задачи разные: статические таблицы — write-once, читаются батчами для аналитики, им хватает плоского chunks → blocks. Динамические — это OLTP с точечными чтениями/записями по ключу, поэтому поверх чанков
  пришлось накрутить LSM-подобную схему: tablet (шардирование под нагрузку), dynamic store (буфер в памяти под свежие записи) и chunk store (то, что уже сброшено на диск).

  важна низкая латентность (миллисекунды) и транзакционность (ACID): перевёл деньги — либо оба счёта обновились, либо ни один. Данные обычно нормализованы (много узких таблиц со связями), индексы — B-tree по ключам, движок
  хранит строки целиком рядом (row-oriented), чтобы прочитать одну строку за один seek. Примеры: PostgreSQL, MySQL, и динамические таблицы в YT — это как раз OLTP-слой.

  OLAP (Online Analytical Processing) — режим под отчёты и аналитику: «выручка по регионам за квартал», «среднее время сессии по когортам». Запросов мало, но каждый сканирует миллионы–миллиарды строк и считает агрегаты (sum,
   count, group by, join больших таблиц). Латентность тут уже секунды–минуты, важна пропускная способность по диску и CPU. Поэтому данные хранят колоночно (column-oriented): значения одной колонки лежат подряд, хорошо
  сжимаются и читаются последовательно, не дёргая то, что не нужно. Часто данные денормализованы (широкие таблицы-«звёзды»), чтобы не делать дорогих джоинов. Примеры: ClickHouse, BigQuery, Snowflake, и статические таблицы в
  YT с MapReduce-операциями поверх — это OLAP.
