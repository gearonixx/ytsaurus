

  BUS — это транспортный слой YT поверх TCP. Сам по себе TCP — это просто поток байтов, ему нужно сверху накрутить «фрейминг» (разбиение на отдельные сообщения), мультиплексирование, всё такое. BUS как раз это и делает:

  - режет поток на фреймы с заголовком (длина, тип, чек-сумма);
  - мультиплексирует много RPC-запросов в одном соединении (несколько параллельных запросов едут по одному TCP без блокировок);
  - поддерживает шифрование, сжатие, attachments (большие куски данных рядом с сообщением);
  - держит persistent connection, переподключается при разрывах.

  Иерархия: TCP → BUS (фрейминг и мультиплекс) → RPC (запрос/ответ с методами) → protobuf (содержимое сообщений). 


----

Чтобы превратить «структурированный запрос» в байты для отправки по сети и обратно. RPC сам по себе только переносит запрос/ответ — а как сериализовать содержимое (id транзакции, путь, опции, флаги), он не знает. Нужен
  формат сериализации, и protobuf — выбранный.

  Альтернативы — JSON, XML, YSON, msgpack, свой формат. Protobuf выигрывает потому что:

  - компактный — числа пишутся как varint (1 байт для маленьких чисел), нет имён полей в байтах, только теги;
  - быстрый — парсинг в разы быстрее JSON;
  - типизированный — .proto-файл это контракт, компилятор сгенерирует классы в C++/Go/Java/Python, и они не разъедутся;
  - расширяемый — добавил новое поле с новым тегом, старые клиенты его просто пропустят, не упадут.
