## Стиль ответов — жёсткие правила

**Длина:**
- Дефолт: 1–3 предложения. Не 2–4, а именно 1–3.
- «что такое X» / «что делает X» / «X?» → одно предложение определения + максимум одно предложение контекста. Всё.
- «проще» / «ещё проще» / «короче» → режь предыдущий ответ минимум вдвое, не переписывай заново той же длины.
- «без воды» / «коротко» / «в N предложений» — жёсткий лимит, считать предложения.
- Псевдокод запросили — давать псевдокод и одно предложение пояснения. Не абзац.
- Длинный ответ только если явно сказано «подробно», «объясни» (без «коротко»), «разверни».

**Запрещено:**
- Преамбулы: «Хороший вопрос», «Разберу», «Окей», «Смотри».
- Саммари в конце: «Итого», «Коротко суть», «То есть».
- Повторять сказанное в этом же чате. Если уже объяснил `BIND`/`TFuture`/`TSharedRef` — не объяснять заново на новый вопрос про них, ссылаться.
- Объяснять термин, который я сам употребил в вопросе.
- Этимология («от англ. ...», «название происходит от ...»), если не спросил.
- Аналогии по умолчанию. Только если прошу «приведи аналогию» или концепция реально без неё непонятна.
- Дублировать в конце ответа то, что было в начале другими словами.

**Follow-up логика:**
- Если задаю follow-up на твой ответ — значит он был непонятен или неполон. Не повторять то же самое другими словами. Заходить с другого угла или копать глубже в конкретную часть.

**Формат:**

## Workflow: комментарии в исходниках

**По умолчанию: после каждого объяснения куска кода автоматически клади это объяснение в исходник комментом `// @gearonixx`, не дожидаясь явного «впиши».** Если объяснил что значит конкретный филд / строка / функция — сразу же дописывай это объяснение над ней. Не спрашивать «дописать?», просто делать.

Стиль — `// @gearonixx @AI_GENERATED@` на отдельной строке (метка `@AI_GENERATED@` через пробел после `@gearonixx`, чтобы потом можно было одним grep'ом отделить заметки, которые написал AI, от заметок самого пользователя), дальше построчно объяснение. Как уже сделано в `bootstrap.cpp`, только без `@AI_GENERATED@` в старых комментариях, написанных вручную.

Все НОВЫЕ комментарии, которые я (Claude) добавляю в исходники, должны иметь обе метки. Существующие пользовательские комментарии с одиночной `@gearonixx` не трогать.

**Куда класть:** над **имплементацией в `.cpp`**, не над декларацией в `.h`. Даже если объяснение про класс целиком — комментарий идёт в `.cpp` над конструктором (`TFoo::TFoo(...)`), не в `.h` над `class TFoo`. Я читаю `.cpp` файлы, заметки нужны там.

Длина комментария = длина последнего устного объяснения. Не раздувать. Если в чате было несколько коротких follow-up'ов про одно и то же — слить их в один связный комментарий, не копировать диалог дословно. Комментарии тоже на русском.

**Уровень разжёванности — для человека с ОСНОВАМИ C++, не для мидла.**

Считается базой и НЕ требует пояснения: указатели, ссылки, классы, наследование, шаблоны (как концепция), `virtual`, `const`, RAII, `std::move`, smart pointers как идея, лямбды, `std::optional`/`std::pair`/`std::vector`, исключения.

НЕ базой — надо разжёвывать или хотя бы расшифровывать жаргон одной фразой:
- Concurrency: lock-free, CAS / compare-and-swap, atomic, мьютексы за пределами «есть гонка/нет гонки», memory ordering, futures/promises, файберы, корутины.
- Системка: epoll/poll/select, syscalls, ABI, vtable layout, NUMA, кэш-линии.
- Сеть: longest-prefix match, RPC pipelining, TLS handshake, HTTP/2 streams.
- Любые YT-специфичные сущности (см. список выше).
- Паттерны типа double-checked locking, copy-on-write, RCU, CRTP — называть и объяснять одной строчкой что это.

Плохой пример (слишком сложно):
```
// Lock-free инкремент через CAS-цикл: compare_exchange_weak может ложно фейлиться.
```

Хороший пример:
```
// Атомарно увеличиваем счётчик на 1, без мьютекса. Идея цикла: прочитали текущее
// значение, попробовали записать value+1 атомарной операцией compare_exchange_weak —
// если кто-то другой успел поменять счётчик между нашим чтением и записью, операция
// не пройдёт, и цикл повторится с новым значением. _weak может срываться даже без
// гонки (особенность процессора), поэтому всегда оборачивают в while.
```

То есть: **называть жаргонный термин (CAS, RAII-guard, lock-free) → сразу же объяснять что он значит на пальцах**. Не предполагать, что я знаю.

## Глоссарий (по ходу разбора)

### NSecurityClient
- `EPermission` — enum: какие бывают права (`Read`, `Write`, `Use`, `Administer`...).
- `TPermissionKey` — вопрос для проверки: «юзер X, путь Y, право Z, можно?».
- `TPermissionCache` — кэш ответов на эти вопросы, чтобы не дёргать мастер каждый раз.

### Coordinator (`TCoordinator`)
- Сервис прокси, держит в Cypress (`//sys/proxies`) реестр всех живых HTTP-прокси: их роли, баны, нагрузка.
- Периодически обновляет свою запись и читает чужие.
- Когда роль этой прокси меняется в Cypress — стреляет сигналом `OnSelfRoleChanged`, на него подписываются компоненты, которым важна роль (например, `TAccessChecker`).

### Логирование
- `YT_LOG_INFO/ERROR/...` — макрос; внутри разворачивается в `Logger().Write(...)`, поэтому в точке вызова имя `Logger` должно быть видно.
- Стандартный паттерн: `static YT_DEFINE_GLOBAL(const NLogging::TLogger, Logger, "Category")` на уровне файла → один логгер на весь `.cpp` со своей категорией.
- На уровне файла (не в классе), потому что лог пишут и свободные функции/хелперы, не только методы класса.
- `static` — внутренняя линковка, запирает `Logger()` внутри `.cpp`, чтобы не столкнуться с одноимённым логгером из других файлов.
